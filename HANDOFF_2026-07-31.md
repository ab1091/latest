# Handoff — 2026-07-31 live testing/debug session → Azure deployment

Context for whichever Claude Code session picks up the Azure deployment work. This project (`azure-online`) is a copy of the working dev project (`~/Desktop/RAG-knowledge`), made specifically to prepare for deploying to an Azure Web App. The database is **not** copied — it's a separate local Postgres instance (see "Database" section below), and migrating it is one of the first things the deployment needs to handle.

## What this project is

Insurance-agency CRM with AI automation. Three services, one shared Postgres DB:
- **ai-service** (FastAPI, Python, port 8000) — SMS/call/webhook AI logic, the automation brain
- **crm-service** (FastAPI, Python, port 8001) — leads/workflows/CRM data
- **frontend** (Next.js, port 3000) — proxies API calls through ai-service

Dockerfiles already exist for all three (`ai-service/Dockerfile`, `crm-service/Dockerfile`, `frontend/Dockerfile`), plus a `docker-compose.yml` at the root — these are the starting point for the Azure Web App container deployment, not built from scratch.

## Bugs found and fixed tonight (2026-07-31, on the dev copy — verify these edits carried over into this `azure-online` copy correctly, it was rsync'd from the dev folder)

1. **Call fired mid-conversation with no consent** — `ai-service/api/sms/router.py`, `_check_call_confirmation` — the classifier prompt conflated "agreed to book an appointment" with "agreed to a phone call." Rewrote the prompt to require genuine explicit call-consent language only.
2. **Appointment email question never actually waited for an answer** — `ai-service/api/sms/router.py` ~line 1586 (`APPOINTMENT EMAIL` guardrail) — the bot asked "Is X still your best email?" but the booking fires automatically the same turn regardless of any reply, so the question was theater. Changed to STATE the literal email address instead of asking.
3. **Duplicate 10-worker scheduler** — both `ai-service/main.py` and `crm-service/main.py` had `workers = max(2, cpu_count())`. ai-service runs its own APScheduler (`core/callback_scheduler.py`) inside every worker's lifespan — 10 workers meant every scheduled job (SMS/call callback polling, stale-lead checks) ran 10x concurrently. Forced `workers = 1` in both files. crm-service has no scheduler of its own, so its multi-worker issue was DB connection pressure (10 × up to 20 pool connections against the same shared Postgres), not duplicate sends — same fix applied for consistency at this scale.
4. **A stale duplicate ai-service process silently survived a "restart"** — confirmed live: killing what looked like the running process left an older process (with its own 10 forked workers) still alive in the background, because two separate process launches had happened without the first ever being killed. **For the Azure deployment: make sure whatever restart/redeploy mechanism you use actually kills the old container/process before starting the new one** — don't assume a "restart" command does this.
5. **`call_outcome_confirmed` stage mapping** (`crm-service/core/lead_lifecycle.py`) — was already fixed in a prior session's diff but silently never deployed because the running process predated the edit. Not a new bug, but a reminder: **code changes require an actual process restart to take effect** — worth double-checking during Azure deploys that the running container actually reflects the latest image/build.
6. **PATCH /api/auth/profile was missing entirely** — frontend called it, backend never implemented it. Added in `ai-service/api/auth/router.py`. Admin profile phone number now saves correctly (used for appointment-booking SMS notifications, `ai-service/core/admin_notify.py`).

## Known open issue — not fixed, just flagged

**Claw Messenger (primary SMS provider) is over its monthly message limit.** Confirmed directly from their own API response (`{"ok": false, "error": "Monthly message limit reached"}` over the live websocket, see `ai-service/core/claw_messenger.py`). The app is currently falling back to Twilio automatically and successfully (`ai-service/api/sms/router.py::_send_sms`, lines ~143-158) — so texts are still going out, just silently through the backup channel. If Twilio also has an issue, there's no third option. The user's account is supposedly $15/mo, 2000 messages — actual DB message count this month (12 agent SMS) doesn't remotely explain hitting that limit, but the DB undercounts real usage significantly (admin notifications aren't logged to the `messages` table at all, deleted-lead testing cascade-deletes history, and the duplicate-worker bug in #3/#4 may have caused extra sends during whatever period it was running). **Check the actual Claw Messenger account dashboard for the real usage number — nothing in this codebase can independently confirm or refute it.**

## Database — the part that actually needs work for Azure

Currently: local Homebrew Postgres 15 on the dev machine, database name `aicrm`, data directory `/opt/homebrew/var/postgresql@15`. Both `ai-service/.env` and `crm-service/.env` point `DATABASE_URL` at `localhost:5432` — **this will not work once deployed**, the Azure-hosted app can't reach a Mac's localhost.

Decision already made with the user: migrate to **Azure Database for PostgreSQL** (flexible server), not keep pointing at the local Mac. Still to do:
1. Provision the Azure Postgres instance.
2. `pg_dump` the local `aicrm` database (schema + data — this has real test data from tonight's session in it, e.g. lead `Bee bee` with a confirmed appointment) and restore it into the Azure instance.
3. Update `DATABASE_URL` in both services' env config to point at the new Azure Postgres host.
4. Confirm `JWT_SECRET` still matches between ai-service and crm-service after the env change (crm-service verifies JWTs issued by ai-service's `/api/auth`) — this was already a documented gotcha in `RUNNING.md`.
